# ozon-agent

Агент для одного кабинета Ozon. Спринт 1 (текущий приоритет, ВБ на паузе —
см. `/root/wb-agent/CLAUDE.md`): `ozon-search` — рекламные кампании
(аналитика/рекомендации) + СЕО текста карточки, тот же сценарий, что и
для WB.

## Доступ — ДВА разных сервиса, разные ключи

- **Seller API** (`api-seller.ozon.ru`) — товары/карточки. Заголовки
  `Client-Id`/`Api-Key` (статичные, `.env`: `OZON_CLIENT_ID`/`OZON_API_KEY`).
- **Performance API** (`api-performance.ozon.ru`) — реклама. OAuth2
  `client_credentials`, ОТДЕЛЬНАЯ пара `.env`:
  `OZON_PERF_CLIENT_ID`/`OZON_PERF_CLIENT_SECRET` (получается в
  seller.ozon.ru → Настройки → API-ключи → Performance API, НЕ то же самое,
  что ключ Seller API — проверено вживую 2026-08-09, обычный
  Client-Id/Api-Key от Seller API даёт 401 на Performance API). Токен живёт
  1800с, обновляется прозрачно в `OzonClient._perf_headers()`.

Рейт-лимиты у Ozon **сильно мягче ВБ** — за сессию отладки (десятки
запросов, включая полный отчёт) ни разу не словили 429. Ограничение
именно на `/api/client/statistics` — **максимум 10 campaign_ids за один
запрос** (иначе `400 "Превышен лимит по количеству кампаний (максимум
10)"`) — `fetch_campaign_stats_batched` уже режет на пачки.

## Статистика РК — асинхронный отчёт (подтверждено вживую 2026-08-09)

1. `POST /api/client/statistics` `{campaigns, dateFrom, dateTo}` → `{"UUID": ...}`
2. Поллинг `GET /api/client/statistics/{UUID}` до `state == "OK"`
   (`NOT_STARTED` → ... → `OK`, заняло ~15с на 2 кампании в тесте)
3. `GET /api/client/statistics/report?UUID=...` → **1 кампания → обычный
   CSV** (`Content-Type: text/csv`), **>1 кампания → zip** с CSV на
   кампанию (`<campaignId>_<from>-<to>.csv`) — код сам определяет по
   содержимому (`_parse_stats_report`), не по количеству ID.

CSV: `;`-разделитель, **первая строка — заголовок-название кампании, НЕ
колонки** — реальные колонки на второй строке
(`_parse_csv_skip_title` их пропускает). Числа — с запятой как
десятичным разделителем (`"0,00"`), при агрегации заменять `,`→`.`.
Один из заголовков колонки — `Средняя ставка (руб.)%!(EXTRA
string=₽)` — это баг самого Ozon (похоже на утёкший `fmt.Sprintf`
формат на их бэкенде), не ошибка парсинга с нашей стороны.

## СЕО / карточка товара — ПРОВЕРЕНО вживую (2026-08-09)

`/v3/product/list` (список, подтверждено). Полные данные карточки — не
`/v2/product/info` (404, устарел, как и `/v1/warehouse/list` у другого
эндпоинта), а **`/v4/product/info/attributes`** (контент/атрибуты) +
**`/v5/product/info/prices`** (цена/НДС, отдельным вызовом — в attributes
их нет).

**Описание хранится как обычный атрибут (`id: 4191`), не отдельным полем**
— важно для любого будущего кода, который трогает СЕО-текст.

`update_product_seo` (`/v3/product/import`) — **подтверждено полным
циклом на живом товаре** (product_id 51483692, offer_id i0851N, 0 продаж
за год — выбран как низкорисковый): дописал тестовую метку в описание →
`status: imported` (async, `task_id` → polling `/v1/product/import/info`)
→ проверил вживую, что текст реально изменился на карточке → вернул
оригинал обратно → проверил побайтовое совпадение с «до». Полный цикл
занял секунды.

**Критично: `/v3/product/import` — full replace, не patch.** В Go-клиенте
у полей нет `omitempty` — если отправить только `name`/`description` без
остального (категория/атрибуты/картинки/цена/вес), API затрёт всё
остальное. `update_product_seo` в коде теперь ВСЕГДА сначала читает
полный текущий снимок (`_fetch_full_product_snapshot`: merge
`/v4/product/info/attributes` + `/v5/product/info/prices`) и патчит
только нужное поле поверх — так же, как проверялось вживую. Не упрощать
обратно до частичного payload.

Побочная находка: импорт вернул `warning` (не `error`) про незаполненный
атрибут «код маркировки» (id 23536) — существовал в карточке ДО правки,
не вызван нашим изменением, но стоит знать, что такие warnings в ответе
возможны и не всегда относятся к тому, что мы поменяли.

## Мутации РК — start/pause ПРОВЕРЕНЫ вживую (2026-08-09)

`start_campaign`/`pause_campaign` (`/api/client/campaign/{id}/activate` /
`/deactivate`) — подтверждены реальным вызовом с явного «подтверждаю»
владельца на кампанию id 27767900 (была INACTIVE → включена

API — подтверждён, есть.

## Бюджет РК (`update_campaign_budget`, найдено и подтверждено вживую 2026-08-09)

`PATCH /api/client/campaign/{campaignId}` — тело `{"dailyBudget": "..."}`
или `{"weeklyBudget": "..."}`, единица — **миллионная доля рубля**
(`1 000 000` = 1₽). Эндпоинт взят из официальной OpenAPI-спеки Performance
API (вытащена из стороннего репозитория `PCDCK/ozon-mcp`, т.к.
`docs.ozon.ru`/`dev.ozon.ru` отдают бесконечный redirect-loop на
непрямые запросы — анти-бот, не открываются ни через WebFetch, ни через
curl).

**Подтверждено полным циклом на живой кампании** (id 27767900, SKU,
INACTIVE — низкорисковая, та же что для start/pause): `weeklyBudget`
10000000000 (10000₽) → патч на 10001000000 (10001₽) → проверил вживую,
что значение реально изменилось → вернул обратно на 10000000000 →
побайтовое совпадение с «до». С явного «подтверждаю» владельца на
конкретный ID.

**Тип бюджета (daily/weekly) фиксируется при создании кампании и не
меняется** — метод сам читает текущий `budgetType` кампании и шлёт
соответствующее поле, чтобы не словить тихий no-op при неверном поле. В
кабинете сейчас: 27 SKU-кампаний на `weeklyBudget`, 1 `BRAND_SHELF` на
`dailyBudget`, у `REF_VK`/`REF_BLOGGER`/`SEARCH_PROMO` бюджета нет
(ставки, не бюджет).

## Управление ставками РК (`fetch_campaign_products`, `fetch_competitive_bids`, `update_product_bids`, 2026-08-09)

Источник эндпоинтов — та же OpenAPI-спека Performance API из
`github.com/PCDCK/ozon-mcp` (`perf_swagger.json`), что и для бюджета;
вытащена свежая копия и перепроверена по актуальному списку из 45 путей.
Важная находка из changelog внутри самой спеки: **фразовое/минус-фразовое
управление ставками Ozon удалил из API 17 января 2024** (поля `phrases`,
`groupId`, `stopWords` убраны из тел запросов) — управление на уровне
ключевых фраз сейчас недоступно через API, есть только read-only отчёт
`POST /api/client/statistics/phrases` (по показам/кликам/заказам на
фразу, в стадии тестирования по документации Ozon).

- `GET /api/client/campaign/{id}/v2/products` (`fetch_campaign_products`)
  — **подтверждено вживую** на кампании 24098195: SKU + текущий CPC-бид +
  название товара. Бид — в миллионных долях рубля, та же конвенция, что
  и бюджет.
- `GET /api/client/campaign/{id}/products/bids/competitive`
  (`fetch_competitive_bids`) — **подтверждено вживую**: ориентир Ozon
  «какой бид нужен, чтобы конкурировать за размещение» по SKU, максимум
  200 SKU за вызов (по спеке, само число не тестировано). `bid: 0`
  означает, что товар не добавлен в кампанию.
- `PUT /api/client/campaign/{id}/products` (`update_product_bids`) — **НЕ
  подтверждено живым вызовом** (только PATCH budget тестировался, PUT
  bids — нет), но путь/схема взяты из той же спеки и совпадают с
  x-code-sample в ней и с полем `bid` из подтверждённого GET-ответа выше
  — достаточно надёжно, чтобы использовать с confirm-gate, как и
  остальные мутации. **По спеке это full-replace списка ставок и
  стоп-слов кампании** — передавать нужно все SKU, которые должны
  остаться с активным бидом, не только изменяемые.

**Находка 2026-08-09 (кампания 24098195, инструмент
`competitor_analysis.py`): 15 из 16 SKU в кампании биддят на 8-18% от
конкурентного ориентира Ozon** (например, наш бид 5₽ при ориентире 63₽).
При этом та же кампания по `daily_report.py` в тот же день показывала
**ДРР 2.8% — отличный результат** (см. запись про кампанию 24098195 в
разделе про схемы CSV выше). **Вывод: `competitive_bid` — это не
«минимальный бид для получения показов», а какой-то более высокий
ориентир (вероятно, топ размещения) — заниженный относительно него бид
НЕ означает, что кампания не работает.** Не использовать этот сигнал как
автоматический триггер поднять ставку — сверяться с фактическим ДРР
перед любым решением.

## Анализ конкурентов через MPSTATS (`competitor_analysis.py`, 2026-08-09, v2)

`python3 competitor_analysis.py <campaign_id> [--no-mpstats]` — для
активной SKU-кампании показывает разрыв между нашими бидами и
`fetch_competitive_bids` (см. выше), плюс реальных именованных
конкурентов (не общий топ ниши) через MPSTATS.

**Наш бренд — `INKI`** (подтверждено вживую 2026-08-09 через Seller API,
`/v4/product/info/attributes`, атрибут id 85 на product_id 51483692).
Код не хардкодит строку — читает через новый `OzonClient.fetch_own_brand()`
(первый товар из `/v3/product/list` → атрибут 85), чтобы не протухнуть,
если в кабинете когда-нибудь появится второй бренд.

**Важно: собственные низкопродажные SKU кабинета не всегда есть в
индексе MPSTATS** — проверено вживую на product_id 51483692 (sku
224479994, тот же товар, что использовался для теста СЕО, 0 продаж за
год) — `ozon-sku.sh ... categories/search_stats/full` вернули
`{"message": "SKU не найден"}`. MPSTATS индексирует по объёму продаж, не
по факту существования товара. Но **на уровне бренда данные есть** (сотни
SKU агрегируются) — поэтому автоопределение ниши идёт через
`ozon-brand.sh INKI niches`, а не через SKU: берётся ниша с максимальной
выручкой бренда (`our_primary_niche`), дальше `ozon-category.sh <ниша>
brands` даёт реальных конкурентов — брендов, а не просто топ товаров
вперемешку с нерелевантными подкатегориями (первая версия инструмента
с ручным путём "Красота и здоровье/Уход за ногтями" вообще не находила
нашу нишу — правильный путь "...Маникюр и педикюр/Уход за кожей и
ногтями/Уход за кутикулой и ногтями"; более широкий путь "...Маникюр и
педикюр" возвращал нерелевантный шум вроде спиртовых очистителей и
маникюрных аппаратов).

**Найдено вживую 2026-08-09: в нише у INKI — `sellers: 56`, но
`sellers_with_sells: 5`** (`ozon-brand.sh INKI niches`) — это не 56
конкурентов, а 56 продавцов, перепродающих САМ бренд INKI (обычная для
Ozon практика арбитража/перепродажи), из них реально продаёт только 5.
Не путать со списком конкурирующих БРЕНДОВ, который даёт отдельный вызов
`ozon-category.sh <ниша> brands` (там `INKI` — один из многих брендов, а
не 56 строк).

**Найдена и исправлена ошибка первой версии: поле `avg_price` в отчёте
MPSTATS по брендам — простое среднее по ВСЕМ карточкам бренда, включая
непроданные** (для INKI: `avg_price=4345₽`, при этом фактическая цена
продаж `revenue/sales=719₽` — расхождение почти в 6 раз, т.к. в каталоге
206 SKU, из них с продажами только 109, и часть непроданных — дорогие
наборы). Сравнение цены с конкурентами в коде считается через
`revenue/sales` (реализованная цена, взвешенная по факту продаж), не
через `avg_price` — иначе разрыв в цене с конкурентами завышался бы в
разы (соответствует правилу sanity-check из mpstats skill: не выдавать
аномальные/невзвешенные метрики как факт без проверки).

**Итоговая находка по кампании 24098195 / нише «Уход за кутикулой и
ногтями»:** INKI — 5-й по выручке бренд в нише (после Milv, BellaStar,
Kottur, FRENCHI), при этом фактическая цена продаж INKI (719₽) на
58-355% выше каждого из топ-8 конкурентов (158-456₽) — то есть INKI
играет в премиум-сегменте той же ниши, а не проигрывает по цене; при
интерпретации разрыва бидов (см. раздел выше) стоит держать это в
голове — премиальная позиция может объяснять, почему кампания и без
высоких бидов даёт хороший ДРР (более лояльная/платёжеспособная
аудитория, а не только эффект самого размещения).

## Статистика РК — ДВЕ разные схемы колонок CSV (найдено 2026-08-09)

Строка-итог кампании всегда есть (`sku == "Всего"`), но набор полей в ней
зависит от `advObjectType`, определяется **по наличию колонки**, не по
типу (надёжнее — не завязано на перечисление типов):

- Если есть `Заказы` → схема "баннерная" (REF_VK/REF_BLOGGER/
  SEARCH_PROMO в проверенных данных): `Заказы`, `Заказы модели`,
  `Выручка, ₽`.
- Иначе → схема "SKU-промо" (SKU/ALL_SKU_PROMO): `Продано товаров`,
  `Продано товаров модели`, `Заказано на сумму, ₽`, и **готовый** ДРР в
  `ДРР (общий), %` / `ДРР в продвижении, %` — не пересчитывать вручную.

**Была реальная ошибка из-за этого**: при первом ручном разборе кампании
`24098195` (тип SKU) её приняли за «потратила 34.7К₽ и получила 0
заказов», потому что смотрели на поле `Заказы`, которого в этой схеме
просто нет (там `Продано товаров`). На деле кампания дала 403 продажи на
533К₽ (ДРР 2.8% — отличный показатель). `daily_report.py:normalize_totals`
теперь учитывает обе схемы — не повторять эту ошибку при ручном разборе
через `verify`/сырые JSON.

## Ежедневный отчёт по рекламе (`daily_report.py`, с 2026-08-09)

Cron `7 5 * * *` (08:07 МСК) → `daily_report.py`: тянет статистику за
**весь предыдущий календарный день** по **всем** активным РК (не по
выборке из 20, как `ozon_client.py report`), считает флаги (`простаивает`
— 0 показов; `расход без заказов` — потрачено ≥300₽ и 0
заказов+модельных заказов; `высокий ДРР` — ДРР>15%, только для схемы с
готовым ДРР), шлёт краткий текст + подробный PDF (`reports/`, в
`.gitignore`) через Telegram-бота `@ramil1985_admin_bot` (тот же канал,
что и алерты по нагрузке сервера — токен из
`/root/telegram-claude-admin-bot/.env`, chat_id владельца хардкожен).
Чистая агрегация без LLM-вызова — можно гонять каждое утро бесплатно.
Пороги (`MIN_SPEND_TO_FLAG`, `HIGH_DRR_PCT`) — константы в начале файла,
править на месте, если отчёт слишком шумный/тихий. Самопроверка схем —
`test_daily_report.py`.
